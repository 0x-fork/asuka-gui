# ネイティブコード

Asuka がラップしていない機能には、**ネイティブパッケージ**を通じてアクセスします。ネイティブパッケージは、モジュール（`native interface`）やビュー（`native component`）を Asuka で宣言するもので、それを各プラットフォームが自身の言語で実装します。iOS と macOS では Swift、Android では Kotlin、Web では JavaScript、Windows と Linux では Go です。`asuka native generate` が、すべての側の型付きのグルーコードを生成します。Asuka からは、モジュールのメソッドをほかのメソッドと同じように呼び出し、ビューを普通のコンポーネントと同じように表示できます。値はコンパクトなバイナリ形式でやり取りされ、JSON もリフレクションも使いません。

```asuka
/// デバイスのバッテリー。
pub native interface Battery {
  /// 充電量で、0 から 1 の値です。
  fn level() -> float
  /// タスクがキャンセルされるまで、充電量が変わるたびに changed を呼びます。
  async fn watch(changed: fn(float))
}
```

```asuka
let battery = try Battery()
let level = try battery.level()
```

```swift
// swift/Battery.swift
final class IOSBattery: Battery {
    func level() throws -> Double {
        UIDevice.current.isBatteryMonitoringEnabled = true
        return Double(UIDevice.current.batteryLevel)
    }
    ...
}
func makeBattery() throws -> any Battery { IOSBattery() }
```

ネイティブパッケージは普通の Asuka パッケージです。アプリの中に置くことも、アプリの依存関係にすることもでき（[パッケージ](packages.md)を参照）、インポートしたアプリにはそのネイティブコードが含まれます。各プラットフォームのコードは、そのプラットフォーム自身のプロジェクト（Swift パッケージ、Gradle モジュール）に置かれ、依存関係もそのプラットフォームのパッケージマネージャー（SwiftPM と Maven）で管理します。

## 必要になるとき

ほとんどのアプリが表示し、使うものは、Asuka のコンポーネントと標準ライブラリ（`asuka/...`）でまかなえます。その一覧は [SwiftUI・Expo との比較](parity.md)にあります。まだ何もラップしていないプラットフォームの API、ベンダーの SDK、Asuka にないビュー（地図、グラフ、一つのプラットフォームにしかないコントロール）が必要になったら、ネイティブパッケージを書きます。

パッケージには、それを使うアプリが動くプラットフォームの分だけコードがあれば十分です。コードがないプラットフォームでは、モジュールを作ろうとすると `unsupported` エラーが投げられ、ビューは何も表示しません（ホストはビューがないことをログに出します）。

## パッケージの作成

```sh
asuka native new ./battery                # Asuka、Swift、Kotlin、JavaScript、デスクトップ向けの Go
asuka native new --projects swift,android ./battery
asuka native add web ./battery            # あとからプラットフォームのプロジェクトを追加
```

`asuka native new` は、すべてのプラットフォームでコンパイルでき、動作するパッケージを生成します。中には、各側で実装済みの `hello` メソッドが入っています。名前を変えて、中身を書いていってください。ネイティブパッケージの構成は次のとおりです。

```
battery/
  asuka.toml               パッケージの名前とバージョン
  battery.asuka            宣言：native interface、native component
  Package.swift            Swift パッケージ（iOS と macOS 向け）
  swift/
    Battery.swift          自分で書く：makeBattery
    Battery.asuka.swift    生成：プロトコル、型、プロバイダー
  android/
    build.gradle.kts       Gradle のライブラリモジュール
    src/main/AndroidManifest.xml          （任意）パーミッション、サービス
    src/main/kotlin/com/example/battery/
      Battery.kt           自分で書く：makeBattery
      Battery.asuka.kt     生成
  web/
    battery.js             自分で書く：export function makeBattery
    battery.asuka.js       生成
  desktop/                 Windows と Linux 向けの Go
  Info.plist               （任意）パッケージが Apple のアプリに求めるもの
  iOS.entitlements         （任意）
  macOS.entitlements       （任意）
```

生成されたファイルは `// Code generated by asuka native. DO NOT EDIT.` で始まり、宣言のハッシュを含んでいます。これらはコミットしてください。

- `asuka dev` と `asuka build` は、ビルドの前に、アプリ自身のネイティブパッケージを生成し直します。そのため、宣言を変更しても、保存すれば反映されます。
- アプリが依存するネイティブパッケージには、生成済みのコードが同梱されています。CLI はそれが宣言と一致するかを確認し、一致しなければ、実行すべきコマンドを示して失敗します。
- `asuka native generate [dir]` で、手動で生成できます。`asuka native check` は古くなったものがあると失敗するので、CI に向いています。

## モジュールの宣言

`native interface` がモジュールになります。

```asuka
/// キッチンのエラー。
pub enum KitchenError: Error {
  /// kitchen: busy
  busy
}

pub enum Level { low, high }

pub struct Item {
  name: string
  weight: float
  level: Level
  tags: [string]
  best: Duration?   // 省略可能
}

pub native interface Kitchen {
  fn name() -> string
  fn items(filter: string) -> [Item]
  async fn cook(recipe: string, progress: fn(float)) -> Item
  fn ask(question: fn(string) -> bool) -> bool
  fn open(name: string) -> Oven
  /// @mainThread
  fn show()
}

/// @mainThread
pub native interface Oven {
  fn heat(to: float, level: Level)
  fn close()
}
```

`Kitchen()` は、プラットフォームの実装を作ります。作成に失敗したときはプラットフォームのエラーを、パッケージにそのプラットフォーム向けのコードがないときは `unsupported` エラーを投げます。プラットフォーム側はいつでも失敗しうるので、どのメソッドもエラーを投げる可能性があり、呼び出しには `try` を付けます。

### 型

| Asuka | Swift | Kotlin | JavaScript |
| --- | --- | --- | --- |
| `bool` | `Bool` | `Boolean` | `boolean` |
| `int` | `Int` | `Long` | `bigint` |
| `float` | `Double` | `Double` | `number` |
| `string` | `String` | `String` | `string` |
| `bytes` | `Data` | `ByteArray` | `Uint8Array` |
| `Duration` | `TimeInterval`（秒） | `kotlin.time.Duration` | `number`（ミリ秒） |
| `[T]` | `[T]` | `List<T>` | `Array` |
| `[string: T]` | `[String: T]` | `Map<String, T>` | `object` |
| `T?` | `T?` | `T?` | `T` または `null` |
| パッケージの構造体 | 構造体（自身を含む場合は final class） | data class | オブジェクト |
| パッケージの列挙型（ケースが値を持たないもの） | ケースごとに static を持つ `RawRepresentable` の構造体 | ケースごとに定数を持つ value class | ケースを収めた凍結（frozen）オブジェクト |
| `native interface`（引数または戻り値） | `any T` | `T` | オブジェクト |
| `fn(...)`（引数） | クロージャ | 関数 | 関数 |

構造体のフィールドは宣言順に渡されます。構造体の定数とメソッドは Asuka 側に残ります。オブジェクト（ネイティブのインターフェース）を渡せるのは引数か戻り値としてだけで、配列、マップ、構造体の中には入れられません。それ以外の型を使うと、`asuka native generate` がその位置とともに報告し、代わりに使うべきものを示します。

### メソッド

- **エラー**：プラットフォーム側が投げたエラーは、次のいずれかとして返ります。
  - パッケージで宣言したエラー（`: Error` を付けて宣言した列挙型のケースで、その `///` ドキュメントがメッセージになります）。プラットフォーム側では、Swift なら `KitchenError.busy`、Kotlin なら `KitchenException(KitchenError.BUSY)`、JavaScript なら `new KitchenError("busy")` として投げます。Asuka では `catch KitchenError.busy` で捕まえられます。
  - `AsukaNativeError.unsupported(msg)`、`AsukaUnsupportedException`、`asuka.native.UnsupportedError`。これらは `unsupported` エラーになります。
  - それ以外のもの。ドメイン（`NSError` のドメインや例外のクラス）、コード、メッセージを持つエラーになります。
- **`async`** を付けたメソッドは非同期になります。Swift では `async`、Kotlin では `suspend`、JavaScript では最初の引数に `AbortSignal` を受け取る `async` 関数です。Asuka は、メインスレッドを止めずにその結果を待ちます。タスクがキャンセルされると（それを始めた画面がなくなったときなど）、プラットフォーム側のタスクもキャンセルされます（Swift のタスク、Kotlin のコルーチン、`AbortSignal` の abort）。ネットワーク、ファイル、ダイアログの応答待ちなど、時間がかかる処理に使ってください。
- **コールバック**：`fn` 型の引数には 2 種類あります。
  - **通知**：何も返さない関数（`progress: fn(float)`）。プラットフォーム側は、呼び出しの実行中でも、呼び出しが戻ったあとでも（ウォッチャーなど）、どのスレッドからでも、何度でも呼べます。Asuka 側ではメインスレッドで実行されるので、状態に書き込めます。
  - **問い合わせ**：何かを返す関数（`question: fn(string) -> bool`）。すぐに実行され、その結果がプラットフォームに返ります。

  コールバックは、それを渡した先のオブジェクトが存在するあいだ有効です。
- **オブジェクト**：メソッドは、ほかのネイティブインターフェースを返せます（`open` は `Oven` を返します）。それぞれがプラットフォーム側では独立したオブジェクトで、Asuka がそれを保持しなくなったとき、または `close()`（`close` という名前の、引数のないメソッド）が呼ばれた時点で解放されます。
- **スレッド**：メソッドはプラットフォーム側で、呼び出したメインスレッドの上で同期的に実行されます。スレッドの切り替えもキューもありません。そのため呼び出しは軽量ですが、時間のかかる呼び出しはメインスレッドを止めてしまいます。そうしたメソッドには `async` を付けてください。
  - メソッドやインターフェースの `///` ドキュメントに `@mainThread` と書くと、必ずプラットフォームのメインスレッドで実行されます。UIKit、AppKit、Android のビューはこれを必要とします。この場合、Swift のプロトコルは `@MainActor` になります。
  - JavaScript はシングルスレッドなので、Web ではこの点は関係ありません。

### 呼び出しのコスト

呼び出しでは、引数をバッファーにエンコードし、境界を一度だけ越えます。iOS では C、Android では JNI、Mac では Swift ライブラリへの関数ポインター、Web では JavaScript のホストを通ります。応答も同じ方法でデコードされます。途中でリフレクションは一切使いません。

## ビューの宣言

`native component` がビューになります。

```asuka
pub native component Segmented(items: [string]) {
  prop selected: int = 0
  event changed(index: int)
}
```

Asuka からは、普通のコンポーネントと同じように表示できます。

```asuka
state selected = 0

segmented.Segmented(["Day", "Week", "Month"]) {
  bind selected: selected
  on changed(i) { selected = i }
}
```

- どのプロパティも、読んでいる値に追従します。値が変わったときに、そしてそのときだけ、プラットフォームのセッターがもう一度呼ばれます。
- イベントはメインスレッドで実行されます。
- ほかの要素と同じスタイルを受け取ります。

各プラットフォームは、ビューをプロトコルとして実装します。プロトコルには、ビュー本体、プロパティごとのセッター、そして作成時に受け取るイベントオブジェクトが含まれます。

```swift
@MainActor final class SwiftSegmented: Segmented {
    let control = UISegmentedControl()
    let events: SegmentedEvents
    var view: AsukaPlatformView { control }          // iOS では UIView、macOS では NSView
    init(_ events: SegmentedEvents) { self.events = events; ... }
    func setItems(_ value: [String]) { ... }
    func setSelected(_ value: Int) { ... }
    // 変更時：events.changed(index: i)
}
@MainActor func makeSegmented(_ events: SegmentedEvents) -> any Segmented { SwiftSegmented(events) }
```

プロパティが届く順番は決まっていません。そのため、二つのプロパティに依存するビュー（項目の中から一つを選ぶものなど）は、受け取った値を保持しておき、両方が揃ってから反映します。ホストは、自前のビューと同じ方法でこのビューのサイズを決めます。

- Swift では `sizeThatFits`（iOS）または `fittingSize`（macOS）。ビューが `AsukaSizing` に準拠していれば、その `sizeThatFits`
- Android では、ビュー自身の計測
- JavaScript では `measure(c)`
- Go では `Measure`（後述）

固有のサイズを持たないビューは、スタイルからサイズを決めます。解放すべきものを持つビューは、`AsukaDestroying` に準拠させるか、JavaScript なら `destroy` を持たせるか、Go なら `native.Destroyer` を実装します。

`examples/media/segmented` は、すべてのプラットフォームで動く完全なビューの例です。

アプリのテスト（プラットフォームのコードがないフェイクホスト上）では、ネイティブビューはコンポーネント名で表示され、`app.tap("Segmented")` はプラットフォームのボタンと同じように `press` イベントを送ります。

## iOS と macOS：Swift

パッケージの Swift のコードは、Swift パッケージとして書きます。パッケージのルートに `Package.swift` を置き、ソースは `swift/` に入れます。一つのパッケージで iOS と macOS の両方に対応し、両者で異なる部分には `#if canImport(UIKit)` を使います。

```swift
// swift-tools-version:5.9
import PackageDescription

let package = Package(
    name: "BatteryNative",
    platforms: [.iOS("16.0"), .macOS("11.0")],
    products: [.library(name: "BatteryNative", targets: ["BatteryNative"])],
    dependencies: [
        .package(url: "https://github.com/egoist/asuka", from: "0.1.0"),
        .package(url: "https://github.com/firebase/firebase-ios-sdk", from: "11.0.0"),
    ],
    targets: [
        .target(name: "BatteryNative", dependencies: [
            .product(name: "Asuka", package: "asuka"),
            .product(name: "FirebaseAnalytics", package: "firebase-ios-sdk"),
        ], path: "swift"),
    ]
)
```

このパッケージは自分のもので、自由に書けます。依存関係、ターゲット、リソース、C ターゲット、バイナリターゲットは、ほかのパッケージと同じく SwiftPM の仕組みそのものです。CLI はこれを、アプリのほかのネイティブパッケージや Asuka のホストとまとめて `xcodebuild` でビルドし、その結果をアプリにリンクして、生成された動的フレームワークとリソースバンドルを埋め込みます。`asuka`（プロダクト `Asuka`）は、生成コードが土台にする Asuka のホストです。CLI はこれを CLI 自身が持つコピーに向けるので、常にアプリの Asuka のコードと一致します。パッケージが宣言する `platforms` も考慮されます。それより古い iOS や macOS 向けにアプリをビルドすると、パッケージが必要とするバージョンを示して失敗します。また、どちらか一方だけを挙げたパッケージ（`platforms: [.iOS("16.0")]`）は、そのプラットフォーム向けにだけビルドされます。

Xcode で編集するには、`Package.swift` を開きます。Xcode は `asuka` をその URL から解決するので、生成コードも自分のコードも、ビルド時と同じように型チェックされます。

自分で書く Swift では、インターフェースごと、ビューごとに関数を一つずつ用意します。必要な関数は、生成されたファイルの先頭に列挙されています。

```swift
func makeKitchen() throws -> any Kitchen
@MainActor func makeOven() throws -> any Oven      // @mainThread のインターフェース
@MainActor func makeDial(_ events: DialEvents) -> any Dial
```

プラットフォーム側で作って Asuka に渡すオブジェクト（`open` が返す `Oven`）も、自分のコードで作ります。バックグラウンドで動くメソッドからメインアクターのオブジェクトを作るには、`try AsukaNative.onMain { SwiftOven() }` を使います。

`Package.swift` の隣に置いた `Info.plist` には、パッケージが Apple のアプリに求めるものを書きます。

- 利用目的の説明文（`NSBluetoothAlwaysUsageDescription`）。アプリ自身の `asuka.toml` にある説明文が優先されます。
- 配列（`UIBackgroundModes`）。アプリやほかのパッケージの配列と結合されます。
- そのほかのキー。アプリが設定していなければ、その値が設定されます。

エンタイトルメントは `iOS.entitlements` と `macOS.entitlements` に書きます。プロビジョニングプロファイルにそのエンタイトルメントがないと、署名付きのビルドは失敗し、それを要求したパッケージの名前が示されます。

## Android：Kotlin

パッケージの Kotlin のコードは、`android/` にある Gradle のライブラリモジュールです。

```kotlin
// android/build.gradle.kts
plugins {
    id("com.android.library")
    id("org.jetbrains.kotlin.android")
}

android {
    namespace = "com.example.battery"
}

dependencies {
    implementation("com.google.code.gson:gson:2.11.0")
}
```

Kotlin のコードは、`src/main/kotlin/` の下の、生成されたファイルが指定するパッケージに置きます。パッケージ名は、パッケージの名前（asuka.toml の `name`）の各部分を小文字にし、ホスト部分を逆順にして先頭に置いたものです（`@acme/battery` なら `_acme.battery`、`github.com/you/battery` なら `com.github.you.battery`）。CLI はこのモジュールをアプリの Gradle ビルドに組み込み、そのビルドが次の設定を行います。そのため、モジュールに書く必要があるのは namespace と依存関係だけです。

- SDK レベル、Java 17、Kotlin のツールチェーン
- Asuka のホストライブラリ（`dev.asuka`）への依存。これにより AndroidX、Material Components、コルーチンも入ります。

モジュールの `src/main/AndroidManifest.xml`（パーミッション、サービス、レシーバー、プロバイダー）は、ほかのライブラリと同じように、アプリのマニフェストにマージされます。

```kotlin
private class AndroidBattery(private val context: Context) : Battery {
    override fun level(): Double { ... }
    override suspend fun watch(changed: (Double) -> kotlin.Unit) { ... }
}
fun makeBattery(): Battery = AndroidBattery(AsukaModules.context)
```

`AsukaModules.context` はアプリケーションのコンテキストで、どのスレッドからでも使えます。`AsukaModules.activity` は、アプリを表示しているアクティビティがあればそのアクティビティで、ダイアログや権限のリクエストなど、アクティビティが必要な処理のためにメインスレッドで使います。ビューのイベントオブジェクトは、そのビューが作られたテーマ付きのコンテキストを持っています（`events.context`）。`AsukaModules.onMain { }` は、Swift の `AsukaNative.onMain` と同じく、メインスレッドでオブジェクトを作ります。生成コードでは Kotlin の `Unit` を `kotlin.Unit` と書くので、自分のコードに `Unit` という名前の型があっても問題ありません。

補完を使ってモジュールを編集するには、アプリの Android プロジェクト（`asuka build --platform android` が書き出します）を Android Studio で開きます。モジュールは、その中に `:native-<package>` として含まれています。

## Web：JavaScript

パッケージの JavaScript のコードは `web/<package>.js` です。これは ES モジュールで、生成された `web/<package>.asuka.js` がインポートする関数をエクスポートします。

```js
export function makeBattery() {
  return {
    async level() { return (await navigator.getBattery()).level; },
    async watch(signal, changed) { ... },
  };
}

export function makeSegmented(events) {
  const el = document.createElement("div");
  return { el, setItems(v) { ... }, setSelected(v) { ... }, measure: () => [216, 32] };
}
```

メソッドは Promise を返してもかまいません。Asuka で `async` でないメソッドでも同じです。パッケージで宣言したエラーは、生成されたクラスで投げます（`import { KitchenError } from "./kitchen.asuka.js"`）。`web/` 内のファイルはすべてアプリに同梱されるので、モジュールは自前のヘルパーをインポートしたり、`import.meta.url` からの相対パスでアセットを取得したりできます。`asuka dev --platform web` では、ファイルが変わるとページがリロードされます。詳しくは [Web](web.md#ネイティブコード) を参照してください。

## Windows と Linux：Go

デスクトップのホストは Go で書かれているので、そこでのネイティブパッケージのコードも Go で、パッケージの `desktop/` ディレクトリに置きます。Windows では `syscall` で Win32 を、Linux では purego で GTK 4 を呼び出し、cgo は使いません。生成される `<package>_native.go` に、自分のコードが用意する関数がインターフェースごとに一つずつ書かれています。

```go
// desktop/battery_windows.go
package battery

func newBattery() (Battery, error) { return winBattery{}, nil }

type winBattery struct{}

func (winBattery) Level() (float64, error) { ... }
func (winBattery) Watch(ctx context.Context, changed func(float64)) error { ... }
```

Asuka で `async` のメソッドは `context.Context` を受け取ります。呼び出したタスクがキャンセルされると、このコンテキストもキャンセルされます。このメソッドは専用のゴルーチンで動きます。`async` でないメソッドはメインスレッドで動くので、メインスレッドを止めてはいけません。プラットフォームの UI に触れる処理（ウィンドウ、GTK のウィジェット、メインスレッドのアパートメントに属する COM オブジェクト）と、すべてのコールバックはメインスレッドで動かします。`native.Post(f)` は f をメインスレッドで実行し、`native.OnMain(f)` は実行して終わるまで待ちます。ファイルはビルド制約でプラットフォームごとに分けます（`windows` と `linux && !android`。Android のビルドも `linux` を満たすためです）。実装がないプラットフォームでは `errors.ErrUnsupported` を返すと、Asuka はそれを `unsupported` エラーとして投げます。

ビューも同じように生成されます。生成されたファイルに、ビューを作る関数とプロパティごとのセッターが書かれ、ビューのイベントオブジェクトがイベントを送ります。

macOS では、パッケージに Swift（`Package.swift`）があればそれが動きます。Go しかないパッケージは macOS でも Go が動きます。

標準ライブラリの Go は、すべてのアプリのホストに入っています。アプリ自身のパッケージにデスクトップ向けの Go があると、それを組み込んでビルドしたホストがアプリに使われます。`asuka build` と `asuka dev` が `go build` を実行します（ビルドするコンピュータに Go 1.26 以降が必要です）。その Go に変更があったときだけビルドし直します。

## ネイティブコードの開発

- **iOS と Android**：`asuka dev` は、ネイティブパッケージを含むアプリの外側をビルドしてインストールし、ネイティブコードが変わったときにビルドし直します。Swift、Kotlin、`Package.swift`、`build.gradle.kts`、`Info.plist`、マニフェストの変更も対象です。アプリの Asuka のコードは、保存するとビルドし直さずにリロードされます。ネイティブパッケージを持たないアプリは、ホットリロードモードで開発用アプリの中で実行されます。開発用アプリに入っているのは、Asuka 自身のネイティブコードだけです。[開発](development.md#スマートフォンでの実行ホットリロードモードとビルドしたアプリ)を参照してください。
- **macOS**：パッケージの Swift は、アプリの Swift ライブラリにビルドされます。こちらも変更があったときだけビルドされ、アプリは状態を保ったまま再実行されます。
- **Windows と Linux**：パッケージの Go はアプリのホストにビルドされます。こちらも変更があったときだけです。
- **Web**：パッケージの JavaScript が変わると、ページがリロードされます。

iOS や macOS でパッケージを初めてビルドするときに Swift の依存関係を解決し、以降のビルドではそれを再利用します。

## 制限

- `asuka build --platform ios --xcframework`（自分の Xcode プロジェクトにアプリを埋め込む場合）は、Swift を含むネイティブパッケージを受け付けません。代わりに、それらの Swift パッケージをそのプロジェクトに追加してください。
- `asuka build --platform android --aar` には、ネイティブパッケージのモジュールは含まれません。埋め込み先の Gradle プロジェクトに追加してください。
- ディレクトリ名が同じネイティブパッケージが二つあると、両方に Swift を持たせることはできません。SwiftPM は、ローカルパッケージをディレクトリ名で識別するためです。
